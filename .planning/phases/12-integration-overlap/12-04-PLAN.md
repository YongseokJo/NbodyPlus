## Objective

Verify that FewBody termination and initialization are unaffected by the async MPI changes in the main force loop.

## Context

FewBody operations happen AFTER the main force loop completes:

1. **FewBody Termination** (lines 315-535): Handles binary mergers, terminations
   - Contains synchronous worker calls: `workers[rank].run_queue()` + `workers[rank].callback()`
   - These are single-particle operations for TASK_MERGE_MANYBODY, etc.

2. **FewBody Initialization** (lines 599-742): Handles new binary formation
   - Contains synchronous worker calls: `workers[rank].run_queue()` + `workers[rank].callback()`
   - These are for TASK_DELETE_GROUP, TASK_MAKE_GROUP

These operations use the synchronous (blocking) pattern intentionally:
- They're event-driven (rare, only when binaries form/terminate)
- They require strict ordering (delete old group before make new group)
- They're not the MPI overhead bottleneck

<task id="4">
Verify worker state is clean for FewBody operations

After the async force loop, workers should be in clean state:
- `on_duty = false` for all workers
- `num_queues = 0` for all workers
- `send_request = MPI_REQUEST_NULL` (async sends completed)

The FewBody operations assume workers are idle. Verify `isComplete()` guarantees this.

In `queue_scheduler.h`, `isComplete()` (line 384):
```cpp
bool isComplete() {
    if (_completed_queues == _total_queues && _assigned_queues == _total_queues)
        return _complete; // returns false
    else
        return _not_complete;  // returns true to continue
}
```

When `isComplete()` returns false (exit loop), all tasks are complete. Workers should be in `_FreeWorkers` set.

Verify `callbackAsync()` properly marks workers as not on duty:
```cpp
void callbackAsync(Worker* worker) {

    worker->callback_async();  // Sets on_duty = false
    if (worker->NumberOfQueues > 0)
        WorkersToGo.insert(worker);
    else
        _FreeWorkers.insert(worker);  // Worker is free
    // ...
}
```

Worker is properly cleaned up. No changes needed.
</task>

<task id="5">
Ensure async receives are canceled/completed before FewBody operations

After the async force loop, there may be pending pre-posted receives. These should be handled:

Option 1: Let them remain (they'll be used next iteration)
Option 2: Cancel them explicitly

The current implementation leaves receives posted, which is fine because:
- Receives are idempotent (no side effects if message never arrives)
- They'll be reset on next `_initialize()` call
- FewBody operations use their own blocking calls

However, to be safe, we should ensure the async state is clean. Add a reset at the end of the force loop:

In `src/irregular_routines.cpp`, after the async force loop closes, reset async state:

```cpp
        } while (queue_scheduler.isComplete());
        // Reset async receive state for FewBody operations (Phase 12)
        // FewBody uses blocking pattern, doesn't need pre-posted receives
```

Actually, no explicit reset is needed because:
1. FewBody operations use `run_queue()` + `callback()` (blocking)
2. These don't use the pre-posted receives
3. Next `initializeIrr()` will reset state via `_initialize()`

No changes needed.
</task>
