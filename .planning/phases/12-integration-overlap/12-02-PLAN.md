## Objective

Ensure CM particle dependencies are preserved with the async pattern. Verify the existing CM iteration logic works correctly with async sends/receives and that CM particles are processed in correct order.

## Context

CM (Center-of-Mass) particles represent binary/multi-body systems. They require special handling:

1. **Separation**: `initializeIrr()` separates CM particles into `CMPtcls` set, single particles into `_queue_list`
2. **Ordering**: Single particles at front of queue, CM particles at back (lines 465-483 in queue_scheduler.h)
3. **Iteration**: During wait loop, CM particles are assigned TASK_AR_INTEGRATION tasks
4. **Worker mapping**: Each CM particle has a dedicated worker in `cm_particle_worker_map`

The current code already handles CM particles during the async window (they're processed while waiting for completions). The async pattern should preserve this behavior.

## Analysis

Looking at the current code (lines 162-191):
```cpp
if (queue_scheduler.CMPtcls.size() > 0)
{
    if (iter == queue_scheduler.CMPtcls.end())
        iter = queue_scheduler.CMPtcls.begin();
    cm_pid = *(iter);
    ptcl = &particles[cm_pid];
    queue.task = TASK_AR_INTEGRATION;
    queue.pid = cm_pid;
    queue.next_time = next_time;
    workers[cm_particle_worker_map[cm_pid]].add_queue(queue);
    queue_scheduler.assignWorker(&workers[cm_particle_worker_map[cm_pid]]);
    iter = queue_scheduler.CMPtcls.erase(iter);
    // ...
}
```

**Key observations:**
1. CM particles are processed one at a time during the wait loop
2. Each CM gets a queue added to its assigned worker
3. `assignWorker()` increments `_assigned_queues` and moves worker to WorkersToGo
4. The worker's queue will be sent on the next `runQueueAsync()` iteration

**The commented-out neighbor check (lines 172-178):**
```cpp
/*
for (int j = 0; j < ptcl->num_neighbors; j++)
{
    if (particles[ptcl->neighbors[j]].is_active && !particles[ptcl->neighbors[j]].is_up_to_date)
    {
        iter++;
        goto skip_to_next;
    }
}

```

This was removed, meaning CM particles no longer wait for neighbor completion. This simplifies async integration - CM tasks can be dispatched immediately.
